# The Command Library, and a local shell that was never running your command

This release is one tool gone over end to end, and a defect found beside it that
turned out to reach further than the tool did. If you use the Local Shell or a
WinRM session, the second half matters more than the first: commands you sent to
them were being typed into the prompt and left there.

## The command you sent to a local shell is now run

Sending a command from the Command Library to a Local Shell or a WinRM session
typed it at the prompt and never pressed Enter. It sat on the continuation line,
looking sent. Both the Send button and the panel that reaches several terminals
did this, and so did the file browser's "go to this folder" and "run in shell".

A line is submitted by a carriage return. What was being sent was a line feed,
which a remote tty translates on your behalf and a Windows console does not, so
the same code was right over SSH and wrong on the machine in front of you. Every
surface that sends a command now uses the same key, and a command that arrives
already carrying one is submitted once rather than twice.

## A local shell that ended the moment it started

A Local Shell session could open, report that it had started, and be over before
you typed anything. It depended on how Heimdall itself had been launched, which
is why it came and went for no reason you could see.

A pseudo console hands its child a console to talk to. Heimdall was not telling
Windows to stop handing that child its own standard handles as well, so when
those were pipes rather than a console, the shell took the pipes, read
end-of-file, and exited cleanly with nothing to say. WinRM sessions share the
same machinery and had the same fault.

Four things around it were repaired in the same pass. The header called a local
shell "via Plink", a remote transport that has nothing to do with it, and now
names the shell it is running. The default shell is taken from the Windows folder
rather than looked up by name, which used to search beside Heimdall first. Each
session was holding two thread-pool threads on a blocking read and now uses its
own. And a session that had already ended could be asked for its exit code
through a handle that was closed.

## Sending one command to several terminals at once

There is a new panel beside the Send button. It lists the terminals you have
open, you tick the ones that should receive, and the command goes to each of
them.

It reaches terminals that are **already open** and never connects one. Every
target receives the same text, so what you read in the preview is what every
machine gets. One confirmation names how many will receive it, whatever the
action's declared risk, because reaching several machines at once is the thing
being confirmed. And a terminal that refuses does not stop the others: the
summary names which did not receive it, and only those stay ticked, so pressing
the button again after fixing one does not run the command a second time on the
four that already worked.

The unit is the terminal, not the tab. A tab split in two holds two terminals,
and they are two different machines as often as not.

## The Command Library, gone over

**The history remembers what you ran, and replays it.** It used to store the
command pattern with the braces still in it and no values, so the panel showed
you `tail -f {path}` and copying gave you exactly that. It now keeps the command
you actually ran, with its parameter values, and either can be put back into the
generator. What it keeps is sealed before it reaches the database, under the
vault's key when the vault is unlocked and this Windows account's own otherwise.
Nothing is recorded while the vault is locked, and rows older than ninety days
are removed.

**A parameter can offer a fixed set of values.** Give it the type `choice` and a
list, and the panel shows a drop-down instead of a text box. What you pick has to
be one of the values offered, matched without regard to case or the spaces around
it.

**The editor tells you when a command and its parameters disagree.** A name in
braces you never declared, or a parameter the command never uses, is pointed out
as you type. It says so and does not refuse: braces are ordinary punctuation in a
shell.

**Tags filter, they do not only rank.** Asking for `prod` used to mean typing it
and getting back everything whose description mentions the word. There is now a
tag list beside the other filters, and the tags of the selected command are shown
with it.

**Enter copies, Ctrl+Enter sends, Ctrl+D duplicates.** Duplicating works on the
commands that ship with Heimdall too, which are not editable, so it is the way to
get a variant of one without retyping it.

**Nine validation messages were reaching you as their own names.** A missing
required parameter produced the literal text `Validation.ParameterRequired` in
the error panel, and had done since the tool shipped. Nothing ever failed,
because a name is a perfectly good string. All nine are translated now, in
English, French and Spanish.

Twenty-two further findings from the same pass are fixed: a search that could
install a stale result and then keep it, filters that silently emptied after
every reload, a risk level arriving from an import that displayed as harmless
while the confirmation treated it as dangerous, and a dialog that could crash the
tool when a library reload landed at the wrong moment.

## Opening a link outside Heimdall

Three places hand a URL to Windows to open: the update banner, the terminal when
a remote host prints one, and the diagram editor when a cell carries a link. All
three required the address to be an ordinary web address before opening it, and
all three said so in their own copy of the same three lines.

They now share one. The rule is unchanged, but it is written once, it is tested,
and the copy that was furthest from anyone's attention is the one whose address
comes from the machine you are connected to.
