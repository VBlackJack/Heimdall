# Root actions in the SFTP browser check the folders on their way

This release makes every root action of the SFTP browser check the folders that lead to its entry, refuses
hard-linked entries in folders other accounts can write, and fixes a selection that grew after a new folder.

## What you will see

### Security

- **Root actions check the folders on their way.** When the SFTP browser acts as root (upload, save,
  download, open for edit, permission change, delete), it now reaches the entry one folder at a time from the
  root folder. A symbolic link on the way is followed only when the link and the folder holding it belong to
  root or to you, and that folder cannot be written by other accounts. Any other link is refused, and the
  message says so: open the folder by its real path instead.
- **Hard-linked entries are refused in folders other accounts can write.** An entry that has another hard link
  is not written, read or changed as root when its folder can be written by an account other than
  root, you and the entry's owner. Hard links in closed folders, such as package files under `/usr`, keep
  working.
- **A root delete removes the entry from the folder it reached.** It is removed by its name from that folder,
  and a file whose name is now a folder is left untouched.

### SFTP browser

- **A new folder no longer adds to the selection.** After "New Folder", the browser selected the new row but
  kept the rows selected before: after two folders the status bar read "3 selected", and a Delete pressed then
  acted on all of them. The new folder, or a renamed entry, now replaces the selection; a plain refresh still
  keeps it.

### Documentation

- **SECURITY describes the root transfers in detail**, in English and French: what the scripts check, what
  earlier versions did, and the limits that remain.

## What to know before you upgrade

- **A link that belongs to another account is no longer followed as root**, even in a closed folder: for
  example a link unpacked from an archive, or a deployment's "current" link owned by a service account. Open
  the real path.
- **A link in a folder that other accounts can write, such as a shared deployment folder, is refused even when
  root made it.**
- **A root delete now needs GNU coreutils on the server**, like the other root actions. On BusyBox or BSD it is
  refused instead of run.
- **A hard-linked entry in a folder other accounts can write is refused as root** for a write, a read or a
  permission change.

## Verified

- Run as root on Debian 12 (dash and bash) and AlmaLinux 9, with the commands exactly as Heimdall builds them:
  links made by root (such as `/var/www` to `/srv/www`) and your own links work for write, read, permission
  change and delete; reading `/etc/passwd` works; hard links in a folder owned by root work; a link owned by
  another account, a root link in a folder other accounts can write, and a file with another hard link in such
  a folder are all refused with nothing changed; nothing is left behind.
- Not tried on screen: the refusal messages in the application, French and Spanish, home folders mounted on
  demand (autofs), the selection fix.

## Limits that remain

- Creating a folder or renaming an entry as root still reaches it through the path as given, links included.
- A new file written as root belongs to root with mode 0600.
- On a folder with a POSIX ACL the mode bits show the ACL mask, and NFSv4 ACLs are not seen.
