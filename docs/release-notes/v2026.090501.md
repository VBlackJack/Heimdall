### Changes

**A saved profile and a typed destination no longer share certificate trust**

- **An RDP certificate approved for one connection could silence the question for another.** The
  trust store keyed every approval by one string, the profile identifier. A destination typed
  into the command palette runs under a quick-connect identifier, and a saved profile can hold the
  very same string: one imported before v2026.090401 reserved that namespace, one edited into the
  inventory by hand, or one brought in by the import of an older installation. Approving the
  certificate for either answered for both, two questions raised at the same moment for the same
  host merged into one, and the trusted certificates screen listed the shared entry under
  whichever name it could resolve.
- Trust is now keyed by an owner: a saved profile, identified by its inventory identifier, or a
  destination typed by hand, identified by its host. The owner is decided by the code that builds
  the connection; nothing reads the shape of the identifier. The durable store, the session-only
  store and the merging of simultaneous questions all carry the owner, so an approval under one
  never answers for the other.
- Approvals for typed destinations live in a new `trustedRdpCertificatesForTypedDestinations`
  entry in settings.json, keyed by the host in lower case, so a quick connect is asked once per
  host. The trusted certificates screen shows such an entry under its host with a "Quick connect"
  badge, never as a deleted profile, and forgetting it leaves a profile with the same identifier
  alone.

**A saved profile with a quick-connect identifier keeps its settings**

- **Connecting such a profile from the command palette dropped its gateway, ports, credentials and
  RDP settings.** The palette told a saved profile from a typed destination by the identifier's
  prefix, and rebuilt a bare profile from the row for anything that matched: host, protocol and the
  protocol's default port, nothing else.
- The palette now routes by where the row came from. A row minted for a typed destination carries a
  mark that only the palette sets and that nothing reading a profile from disk can set. A saved
  profile is dialled through the server list with its whole profile, whatever its identifier says.
- The import of an older installation copied each profile's identifier verbatim and could still
  create a profile in the reserved namespace on first launch. It now assigns a fresh identifier to
  such a profile and logs it, as the ordinary import already did.

**A setting's range is declared once, and the loader and the screen agree on it**

- **The settings screen and the settings loader disagreed on several bounds.** Each bound was
  written by hand in four places, and they had drifted: the screen refused a tunnel establishment
  delay above 30 seconds that the loader accepted up to 60, and the loader warned about an
  anti-idle interval of 0, the value that turns the timer off and that the screen had always
  accepted. Six settings had a bound on the screen and none in the loader.
- Each ranged setting now carries one declaration, and the loader's warnings, the screen's
  validation and the message it shows, in both languages, are derived from it. A setting whose
  "off" value is zero declares that too, and the loader no longer warns about it.
- Two bounds moved where the two sides disagreed: the tunnel establishment delay is 0 to 60000 ms
  on both sides, and the anti-idle interval is 0 for off or 10 to 3600 seconds on both. The update
  check interval, the terminal font size, the external tool timeout and the three session health
  monitor settings are now bounded in the loader as well, so a hand-edited value outside the range
  is warned about.

**An out-of-range setting is logged as kept, not as corrected**

- A setting outside its range, edited into settings.json by hand, was logged as "outside the valid
  range" and then used exactly as written. The sentence read as a correction the loader never
  made. It now says the value is outside the recommended range and that the loader keeps it as
  written. Nothing is clamped: the loader still preserves what the file says, and each setting
  decides at its use site whether an out-of-range value bites. See the Settings FAQ, section
  "Where a setting's range lives, and what happens outside it".

### Notes

- **What this costs.** Certificate approvals given to typed destinations before this version stay
  under the profile key they were written with. They are not moved: nothing on disk records which
  owner wrote them, and deciding by the identifier's shape is the mistake being ended. A quick
  connect to such a host is asked once more; the old entry stays listed on the trusted
  certificates screen and can be forgotten there.
- **A correction to the previous notes.** v2026.090403 said, under "What remains open", that a
  saved profile holding a quick-connect identifier still shared its certificate trust key with a
  typed destination, that importing an older installation could still create such a profile, and
  that profiles imported before v2026.090401 remained affected. None of the three holds any more:
  the trust key carries its owner, the legacy import assigns a fresh identifier, and a profile
  that still holds such an identifier is dialled as a profile and trusted as a profile.
- The rename migration withdrawn by v2026.090403 stays withdrawn. No profile identifier is
  rewritten by this version.
- A saved profile in the reserved namespace is still not renamed and can still exist; it is now
  harmless. See SECURITY, section "RDP server certificate trust".
