# The master password protects every stored secret, and root browsing works under stricter servers

This release makes turning the master password on or off cover every place Heimdall keeps a secret, and fixes
root browsing, sudo-rs messages and server commands for accounts whose login shell is not a Bourne shell.

## What you will see

### Master password

- **Turning it on seals every stored secret.** Gateway passwords, remembered shared-session passwords, the
  password generator presets and the command history are now sealed with the master password too. Before, only
  the session passwords and two settings were, against what the settings help said.
- **Turning it off makes every secret readable again, or changes nothing.** Before, the secrets of those four
  places stayed sealed with a key that was then erased, and could never be read again. Now Heimdall checks that
  nothing is still sealed before and after it erases the key. If anything is left, or anything fails, the key is
  put back, everything is sealed again, and the message names what could not be done. A turn-off interrupted
  by a crash or a shutdown is finished at the next start.
- **A secret saved in the old form while the master password is on is sealed at the next unlock.** For example a
  gateway edited before turning the master password on and saved after.
- **The backup copies of the settings and session files follow.** They no longer keep secrets in the old form
  after a refused turn-off or an interrupted one.
- **The turn-off window says** that copies of your Heimdall data files made while the master password was on,
  such as backups, cannot be read once it is off. Exports are not affected: they never contain passwords.

### SFTP browser as root

- **Browsing as root works with a sudo rule limited to find.** The listing command given to sudo is now `find`
  itself. Before, it started with a locale setting that servers with a stricter sudo policy refuse.
- **sudo-rs is understood.** On servers that use sudo-rs (Ubuntu 25.10 and later), a wrong password, a missing
  password and a refusal are now recognised like with sudo: a refused password stops a batch at the first entry.

### SFTP commands and login shells

- **Uploads, server-side copy, delete and the check before a transfer work when your login shell is csh, tcsh,
  zsh or fish.** Under zsh (the default on macOS servers) or tcsh, an upload or a server-side copy that should
  have been refused because the destination already existed could be reported as done, while the new content
  was discarded. The commands now run their steps through `sh`, and a `!` in a file name is handled.

## What to know before you upgrade

- **Secrets already lost by a turn-off with an earlier version cannot be recovered**: the key that sealed them
  was erased then.
- **Turning the master password on or off now also processes the command history**, which can take longer with
  a large history.

## Verified

- Turning the master password on and off on screen with a test data folder: a session password and a gateway
  password, a gateway saved after turning it on and sealed at the next unlock, no sealed value left anywhere
  after turning it off, start without a password afterwards.
- Run in a Debian 13 container with the commands exactly as Heimdall builds them: server-side copy, publish,
  delete and the check before a transfer under sh, tcsh and zsh with names holding a quote, a space and `!`;
  root browsing under a sudo rule limited to find, also under a stricter policy; sudo-rs 0.2.5 messages for a
  wrong password, a missing password and a refusal; a new file written as root.
- Not tried on screen: a refused or interrupted turn-off, Windows Hello during a turn-off, the new window text in
  French and Spanish, fish.

## Limits that remain

- After turning the master password on, the command history database may keep old values in its free pages
  until it is compacted.
- Network tools (port scan, DNS, TLS and similar) still send commands that a csh or tcsh login shell does not
  understand.
