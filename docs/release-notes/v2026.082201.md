This release closes a defect that had been consuming your machine quietly for as long as Heimdall
has existed, and adds the two reference pages people kept needing.

### Opening and closing Remote Desktop sessions no longer costs the machine

Every Remote Desktop session left something behind. Opening one and closing it consumed around 60
system handles that Windows never got back, and it made no difference whether the session connected
or failed on the first attempt. A day of ordinary use, which is precisely opening and closing
sessions, accumulated thousands of them.

Nothing showed it. The Windows task manager reports memory, and these resources are not memory, so
the count could climb all day without a single number moving on screen. That is why it went
unnoticed for so long: it was found while investigating something else.

The cost belongs to creating the Remote Desktop control, not to connecting with it. Heimdall now
keeps a control and hands it to the next session instead of building a new one each time. Measured
over the same cycles as before, the handle count no longer grows at all.

The control is scrubbed between sessions. Its stored password is overwritten, its settings return to
their defaults, and one that has met a fatal error is destroyed rather than passed on. A session
never inherits anything from the session before it.

One honest caveat: because these resources are not memory, this is unlikely to change the memory
figure you see in the task manager. It is a separate defect that was found while looking into that
one, and it is worth fixing on its own account.

### Two new pages, and a setting that was telling you the wrong thing

A settings FAQ now covers the options that are not self-explanatory. It includes the two locks that
are easy to confuse, and the distinction matters: the application PIN is a screen lock and encrypts
nothing, while the master password derives a key that actually encrypts your stored credentials.
Setting the first while meaning the second gives far less protection than it appears to.

A second page gives what a Remote Desktop session actually costs in memory, measured rather than
estimated, and which settings change that number. Most of them do not, and the page says so instead
of repeating advice that sounds plausible.

Both pages state plainly that "Bitmap caching" does not do what its name suggests. It controls
whether the cache is kept on disk between sessions. It does not control the cache in memory, so
turning it off frees nothing, and it costs you the redraws the disk cache would have saved. That is
a naming problem on our side, and it is being treated as one.

### A prefilled Base64 tool could run twice at once

Opening the Base64 tool with text already in it started an encode that ignored the rule the buttons
follow. It could begin while another run was already in progress, and it could let a button start
another over it. The tool now refuses in both directions, as it already did between two clicks.

### The hash generator's file drop zone now agrees with itself

The browse button, the drop border and the drag cursor all answer one question: whether the tool
will take a file. They used to answer it from two different places, and after the tool was closed
they disagreed outright, leaving the button enabled over a zone that refused everything. They now
read the answer from one place.
